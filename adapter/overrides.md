# Operator overrides

These are pstack defaults, not new permissions. The user's request, project instructions, tool permissions, and budgets take precedence. Within pstack they override conflicting upstream instructions.

- Size the task before routing it. A task with a clear scope, a known method, and a check you can really run is done directly, with a minimal real check. It gets no playbook checklist, no subagent, and no independent review unless the user asks. A read-only question is answered without touching files. A plan-only request stays a plan.
- Fix only what the request needs. A defect that does not block the current step goes in the reply as a one-line follow-up with its evidence. Do not fix it, however small, unless the user asks. This overrides "mid-run discoveries are yours", "just do it", and self-healing instructions. A full-autonomy grant applies only within its stated scope.
- Spawn a subagent only when the task needs its parallelism or its independence, or when the user explicitly requests that process. A read-only question or easily verified edit alone does not justify delegation. Independent review needs a fresh context and a fixed artifact, not the author's conversation or self-evaluation. If the backend is missing, stop that step and name the gap. Collect started work before declaring completion; report pending work honestly. Bound retries and spend, do not keep starting replacement panels after repeated service failures.
- Read a principle's leaf skill when it changes a decision. By default the reply names no principles, playbook steps, checkpoints, or skills. It says what changed, what the user will notice, and the evidence. If the user asks for process details, provide them.
- Reply in the language the user writes in. Make clear which claims were measured, inferred, or remain unknown; do not mistake tests passing for complete surface verification.
- Leave changes uncommitted unless the user asked for commits. Push, open or update a pull request, merge, deploy, bump a version, or send an external message only when the user asked. "Opening a PR" at the end of a playbook applies only then. Never bypass approvals, change global settings, install optional packages, or widen another tool's authorization based on a skill alone.
