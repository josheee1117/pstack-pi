# Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after [babysit](babysit.md). Landing requires explicit authorization: an armed auto-merge, a merge command, or a push to a shared branch is an irreversible action. Babysitting never grants it.

Read [`../references/execution.md`](../references/execution.md) before step 1. The verifier in that step must be a context that did not write the PR, on an independent session under the package default, and it gets the requirement plus the pinned head SHA, never the author's self-report.

1. **Resolve the forge, then verify every PR independently.** The forge is what the project declares in its `AGENTS.md`, defaulting to `gh`. One verifier per PR, not batched, each with a context that did not write that PR. Batching verdicts into one pass is the thing this step exists to prevent. Each verifier exercises the real surface against parent and head, then returns `PASS`, `PASS+NOTES`, or `FAIL`, and posts that verdict on its own PR. Safe means a verdict from someone who did not write the code. A green CI run is not a verdict. A bot approval is not a verdict.
   - When no independent verifier is available, say so and stop. Do not verify your own PR and call it independent.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` count as passing. A verified PR sitting above an unverified one is not landable. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that each verdict still describes the patch.** Record the verdict's head SHA, base SHA, and the stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing, compare the recorded patch-id with the current one, and re-check the base too: a move of the base branch alone is enough to change what the head means, and a head-only protection flag (`--match-head-commit` or its equivalent) does not catch it. When the patch changed, re-verify. When it did not, keep the code verdict but re-run mergeability and CI at the current head and base. A matching commit message or a green check from an older SHA is not a substitute. Do not claim this reaches the safety of a purpose-built landing tool: it is a comparison the operator can audit, not a guarantee.
4. **Prepare only the bottom PR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that PR to trunk. Re-run step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** If the bottom PR is mergeable now, squash it. If requirements are still running and the user asked for merge-when-ready, arm only that PR. Wait for that PR to merge before preparing the next one.
6. **Do not read an auto-merge request as stack readiness.** It says at most that auto-merge was requested for one PR. It does not prove the parent's merge state, that a descendant is queued, that a patch verdict is current, or that the run is contiguous. Confirm the current bottom PR's real state, and say the state is unknown when the forge cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, drop the merged PR from the frozen bottom-to-top list, and inspect the new bottom PR's base, head, checks, and patch-id. A host may retarget a child automatically; do not assume it did. Repeat steps 3 through 6 for that one PR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** Poll or watch the current PR with the forge CLI, re-reading it after each wake, and ignore a generic "ready to merge" signal until the PR actually reports merged. Hard-fail only when the PR is closed without merging, a required check concludes failing or cancelled with no auto-merge pending, or the merge state reports a real conflict with no auto-merge pending. A blocked state while checks are pending or auto-merge is armed is not failure. Hold the watch with the session's wake mechanism (see [autonomous-run](autonomous-run.md)), or on a bounded poll budget when there is none. Report each merge and the new ceiling. Diagnose a stalled queue before mutating it.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply.** The verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
