# Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean independent verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

Read [`../references/execution.md`](../references/execution.md) before spawning owners. Each owner is an independent Pi session in its own exclusive worktree under the package default, and step 4's verification must come from a context that did not write the PR.

This playbook merges and lands. Run it only on an explicit full-autonomy grant, and only when the operator names the queue.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator: the operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, register the program objective as the session's goal so it survives turns.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program; the project's `AGENTS.md` declares it, defaulting to `gh`. One independent session per PR owns build, the first push, a ready PR, self-proof on the real artifact ([prove-it-works](../references/principles.md#prove-it-works)), skeptical review-bot triage per [`../references/bugbot-triage.md`](../references/bugbot-triage.md), `pstack-no-comments`, a rebase onto current trunk, the babysit loop to green ([babysit](babysit.md)), and the merge itself. Within about 15 minutes every owner starts a `decisions.tsv` trail per `pstack-show-me-your-work`, pushes its first branch snapshot, and opens the PR ready, never draft. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep the trail uncommitted and return it with the report. The rebase always precedes babysit and never waits for drift or conflicts. The merge is the one step an owner may not take alone; step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off trunk, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Independently verify every merge-ready head before its merge.** At the owner's merge-ready head SHA, run parallel independent verifiers per `pstack-swarm` and aggregate to one verdict. The lanes: rerun the gates at that SHA. Prove the load-bearing behavior on the real surface the change touches. Audit the receipts and the diff, distrusting the PR body. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for, instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. Findings go back to the owner for fix-forward, and a new head gets a fresh verification and a fresh verdict.
5. **On a clean verdict the owner merges and takes the next item.** The owner merges only from a head freshly rebased onto trunk. The merge-ready report is made at a trunk-current head, and the verdict pins that SHA. If trunk moves again before the merge, the patch-id rule in [shipping](shipping.md) governs re-verification. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge and picks up its next self-contained item. The operator's autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value needs your fresh countersign, granted only after verifier proof. Absorbing values that already landed on trunk is drift, not a raise. Audit each active owner roughly every 30 minutes of wall clock. That cadence needs a real timer, so establish one of these before you start and say which you used: a recurring wake the environment itself fires, or a bounded poll loop you hold. A status field on an owner, a message arriving from another session, and a completion notification are not timers. When the environment fires nothing and you cannot hold a poll loop, say so up front, audit at natural boundaries instead, and never tell the operator a tick is armed when nothing will fire it. At each audit, re-read this playbook from trunk and re-read the registered goal, then check the operation against both and fix drift in that audit. Probe each owner with a status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and report files. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. When merges batch, run a retro pass and a post-merge bot-comment sweep.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner immediately as a zero-writes order. Owners hold their briefs until the operator releases them.

**Reply.** The queue with each PR's owner, state, and head SHA. Each verdict and the verification that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
